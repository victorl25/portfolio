# Version 2 Refactoring

## Objective

Version 2 will enhance the application and will add the following capabilities:
- enhance ability to track cash generated by dividend payouts and option transactions
- improve tracking of the portfolio balance impacted by the active short sales and covered calls/puts
- add ability to track portfolio balance changes over time
- add ability to report realized taxable gains and losses

The key questions that the application aims to answer are:
- what is the current net worth of my equity portfolio?
- how much did my portfolio change YTD or over 1 year?
- what is the portfolio change trend/chart?
- what is the composition of my portfolio by investment themes?
- what are my realized taxable gains and losses YTD?
- how the individual assets are performing?

## Summary

Version 2 will implement a substatial refactoring of the application and feature enhancements:
- the application will now track individual transactions including dividend payouts and option transctaions
- the ledger table will still reflect current state of the portfolio as a summary of held equities
- the ledger state will be recalculated after each equity transaction and will hold one active record per account + symbol pair with the quantity held and the remaining cost basis (equities only, no options)
- the application will track/store daily closing prices for all active assets instead of the current price quotes
- the options table will be added to track open option positions, one active record per account + option symbol, recalculated after each option transaction in the same way as the ledger
- asset notes will be moved into a seperate table (Notes) to track history of notes

## Schema changes

Info table will be added - database metadata, a single record:
- Schema_Version (version of the database schema, text, e.g. "2.0")

The Schema_Version is set when a new database is created. When a database is opened, the application reads the Schema_Version to check compatibility. Databases created before version 2.0 (without the Info table) are not migrated: the application refuses to open them and shows an explanation. In that case (including the automatic load at startup) the application continues with a new empty database. Future schema changes increment the Schema_Version and add an upgrade step from the previous 2.x version.

Accounts table - there are no changes to the Accounts table

Transactions table will be added:
- Transaction_ID (primary key, integer, auto incremented)
- Account_ID (foreign key to Accounts table, indexed)
- Date (date of the transaction `YYYY-MM-DD`, indexed)
- Type (vocabulary: Cash, Trade, Record, Other; Cash transactions only impact the account balance, Trade transactions impact the account balance and the asset ledger, Record transactions impact only the asset ledger, Other transactions are just for the information purposed)
- Symbol (stock, ETF or option symbol, text, checked for validity upon insert, nullable e.g. for Cash transactions)
- Quantity (number of shares/units bought/sold, float, positive number means bought, negative number means sold)
- Price (price per share/unit, float)
- Amount (net cash impact of the transaction on the account's cash balance, float, positive number means cash received, negative number means cash paid; taken from the import file's Amount column if available, net of commissions and fees, otherwise calculated as -Quantity × Price (× 100 for options); 0 for non-cash transactions)
- Currency (text, default USD)
- Description (description of the transaction, populated from the column mapped to Action in the import file, text)
- Category (vocabulary: Equity, Option, Dividend, Fee, Interest, Margin, Tax, Transfer, Other)
- Effect (how the transaction was applied, vocabulary: Trade, Cash, Other, Distribution, Split, Merger, Reinvestment, RSU, Snapshot; copied from the matched import rule, Snapshot for holdings recorded by Import Holdings; used to re-apply the transaction when it is edited or when the ledger is rebuilt)
- Hash (hash value computed from account, date, symbol, quantity, price, and amount for a quick validation and duplicate detection, indexed)
- Timestamp (datetime stamp of the transaction entry `YYYY-MM-DD HH:MM:SS`, indexed)
- Valid (flag whether the transaction is valid, default is yes, invalid transactions are considered deprecated)

Transactions can be edited or deleted in the Transactions view:
- Edit - if the active Ledger (or Options) entry for the transaction's account + symbol references the edited transaction, that entry is marked inactive and a new entry is built from its Parent entry plus the edited transaction. Otherwise the edited transaction is applied in full, the same way as a newly imported transaction; the original transaction's effect remains in the ledger, so a warning is displayed that the ledger might need to be rebuilt.
- Cash - if the Amount of a transaction is edited, the delta (new Amount - previous Amount) is applied to the account's cash balance.
- Delete - the transaction is marked invalid (Valid = 0). If the transaction is referenced by any Ledger or Options entry (active or inactive), a warning is displayed that the ledger might need to be rebuilt and the user is asked to confirm the deletion. The Ledger and Options entries are not changed automatically, but the deleted transaction's Amount is reversed on the account's cash balance (the Amount is subtracted from the balance).

Assets table - notes are extracted from the Assets table and moved to a separate table called Notes.

Notes table will be added:
- Symbol (stock or ETF symbol, foreign key to the Assets table)
- Timestamp (datetime stamp of the note entry `YYYY-MM-DD HH:MM:SS`)
- Note (text, free-form user note)

Prices table will be modified to track price quote date instead of the timestamp:
- Date (date stamp of the price quote `YYYY-MM-DD`, indexed)
- Symbol (stock or ETF symbol, foreign key to Assets)
- Price (price per share, float)
- Currency (text, default USD)
- Valid (flag whether the price quote is valid, default is yes, invalid price quotes are considered deleted)

Ledger table - current snapshot of held equity positions, one active record per account + symbol pair. Options are not stored in the Ledger.
- Holding_ID (primary key, integer, auto increment)
- Parent_ID (foreign key to the Ledger table, parent ledger entry, nullable)
- Transaction_ID (foreigh key to the Transactions table, link to the last transaction that modified the ledger entry)
- Timestamp (datetime stamp of the ledger record `YYYY-MM-DD HH:MM:SS`, indexed)
- Account_ID (foreign key to Accounts table, indexed)
- Symbol (asset symbol can include stock, ETF, mutual fund)
- Quantity (number of units held with the recorded cost basis, float)
- Cost_Basis (total remaining cost basis of the held shares, float; the averaged cost basis per share is Cost_Basis / Quantity)
- Currency (text, default USD)
- Active (flag whether the ledger entry is active, default is yes, inactive entries are considered superseded or eliminated)

Ledger entries are updated when a Trade or Record transaction is added. Each active ledger entry is uniquely identified by the account + symbol. A new ledger entry is derived from the existing ledger entry (the Parent) plus the transaction: quantity and cost basis are updated based on the transaction info as shown below (q and C are the parent entry's quantity and cost basis, Δq is the transaction quantity). The existing ledger entry is marked inactive and the updated ledger entry is added with the current timestamp, Parent_ID set to the previous entry and Transaction_ID set to the transaction.

| Transaction | New quantity | New cost basis |
|---|---|---|
| Buy (Trade, Δq > 0) | q + Δq | C + (-Amount), i.e. the purchase cost including fees |
| Sell (Trade, Δq < 0), long position | q + Δq | C × (q + Δq) / q, i.e. average cost reduced proportionally |
| Sell more than held, or buy to cover a short position | crosses 0 | the part that closes the position uses the proportional rule; the part that opens the opposite side starts a new cost basis at the transaction's price |
| Distribution | q + Δq | C (0 if new entry) |
| RSU | q + Δq | C + Δq × closing price of the stock on the transaction date |
| Split | Δq (replaces the quantity) | C (0 if new entry) |
| Snapshot (Import Holdings) | quantity from the file | cost basis from the file |

If a ledger entry's quantity becomes 0, the entry remains active (a later transaction for the same account + symbol supersedes it); entries with quantity 0 are not shown in the Portfolio and Ledger views, are not considered by Update Prices, and are excluded from reports.

The ledger of an account can be rebuilt by replaying the valid transactions of each account + symbol pair in chronological order, on a special request from the Ledger view. A warning is displayed before the rebuild that it discards any manual edits of the account's ledger entries. The recalculated ledger entries supersede the existing entries. Ledger entries can also be manually edited via the form on the Ledger view.

Options table will be added - current snapshot of held option positions, one active record per account + option symbol slot (works the same way as the Ledger table):
- Option_ID (primary key, integer, auto increment)
- Parent_ID (foreign key to the Option table, parent option entry, nullable)
- Transaction_ID (foreigh key to the Transactions table, link to the last transaction that modified the option entry)
- Timestamp (datetime stamp of the option record `YYYY-MM-DD HH:MM:SS`)
- Account_ID (foreign key to Accounts table, indexed)
- Symbol (option symbol, e.g. NVDA20260101C300)
- Asset (underlying asset symbol, e.g. NVDA)
- Expiration_Date (option expiration date `YYYY-MM-DD`, indexed)
- Strike (strike price, float)
- Quantity (net number of contracts held, integer, positive for bought calls/puts, negative for sold calls/puts)
- Cost_Basis (total remaining cost basis of the option lot, float; premium paid is positive, premium received is negative; the averaged cost basis per contract is Cost_Basis / Quantity)
- Currency (text, default USD)
- Active (flag whether the option record is active, default is yes, inactive records are considered superseded or closed; expired options do not have to be closed explicitly, the expiration date already provides the necessary info)

The Options table behaves very similarly to the Ledger table, using the same quantity and cost basis rules. A new option transaction adds or replaces the option entry for the account + option symbol combination. Option entries with quantity 0 remain active until manually deactivated, but are not shown in the Options view. Getting the current option value might be tricky and options may or may not be considered for the overall portfolio value. 
Option entries are recalculated together with the ledger when an account's ledger rebuild is requested. Recalculated option entries supersede the existing ones.

Mappings table:
- Mapping_ID (primary key, integer, auto incremented)
- Header_Hash (hash of the CSV file's header row, text, indexed; identifies the file layout the mapping belongs to)
- Source (transaction field key: Account | Name | Date | Action | Symbol | Description | Quantity | Price | Amount | CostBasis | CurrentValue | Currency; unique per Header_Hash)
- Target (CSV column name from the source file)
- Pattern (optional regex; if set, applied to the source value — first capture group used, or full match if no group)

When a CSV file is imported, a hash of its header row is computed (after removing a byte order mark and trimming each column name). The column mapping dialog is pre-populated with the mappings stored for that Header_Hash. When the user confirms the mapping dialog, each Source → Target mapping is stored in the Mappings table linked to the file's Header_Hash: a new record is added for a new Header_Hash + Source pair, and an existing record is updated if the mapping changed. Files with different header rows therefore keep separate mappings, even if they contain identically named columns (e.g. a "Price" or "Amount" column in files from different brokers, or in account and transaction files from the same broker).

Rules table will be added - import rules used to interpret the Action column of imported transactions:
- Rule_ID (primary key, integer, auto incremented)
- Rule_Order (integer, rules are evaluated in ascending order and the first matching rule wins)
- Pattern (regular expression matched against the Action value, text)
- Case_Sensitive (flag whether the Pattern is matched case sensitive, default is yes)
- Symbol_Required (flag whether the rule requires a non-empty Symbol; if set and the row's Symbol is empty, the rule is not attempted and matching continues with the next rule, default is yes)
- Category (category assigned to the transaction based on the rule matching), used verbatim except for the following cases:
    - Asset - resolve as Equity or Option category based on the symbol (option symbols have a special pattern)
- Effect (what the import does with the matched transactions, vocabulary: Ignore, Trade, Cash, Other, Distribution, Split, Merger, Reinvestment, RSU)
    - Ignore - the transaction is ignored and not recorded (counted as "ignored because of the import rules")
    - Trade - a new entry type=Trade is created in the Transactions table to reflect equity/option trade (); the Ledger or Options table is updated to reflect asset changes, and the account's cash balance is changed by the transaction Amount. 
    - Cash - a new entry type=Cash created in the Transaction table and the account's cash balance is changed by the Amount; Ledger and Options are not affected
    - Other - a new entry type=Other created in the Transaction table and nothing else is affected
    - Distribution - a new entry type=Record created in the Transactions table, the transaction Amount is set to 0 regardless of the import data, Ledger or Options are updated to _adjust_ the symbol's quantity by the transaction quantity (new entries are created if they don't exist for the symbol) and the cost basis is kept the same as in the parent ledger entry, or set to 0 if a new ledger entry.
    - Split - a new entry type=Record is created in the Transactions table, the transaction Amount is set to 0 regardless of the import data, Ledger or Options are updated to _replace_ the symbol's quantity with the transaction quantity (new etries are created if they don't exists for the symbol) and the cost basis is kept the same or set to 0 if a new ledger entry.
    - Merger - a new entry type=Other is created in the Transactions table, the transaction Amount is set to 0 regardless of the import data
    - RSU - vested restricted stock units: a new entry type=Record is created in the Transactions table, the transaction Amount is set to 0 regardless of the import data (no cash is paid), and the Ledger is updated to _add_ the transaction quantity (a new entry is created if it doesn't exist for the symbol). The cost basis of the vested shares is calculated from the asset (stock) price on the transaction date times the quantity and added to the parent entry's cost basis. The price is the stock's daily closing price on the transaction date from the Prices table (the last close within the 7 days before it when the date is not a trading day); if it is not stored yet, it is retrieved with the Yahoo Finance MCP get_chart tool before the import and added to the Prices table. The price used is stored as the transaction's Price (the price column of the import file is ignored), so edits and ledger rebuilds use the same cost basis. If no price can be found, the transaction is recorded with an empty Price (cost basis 0) and listed in the import summary so the price can be entered in the Transactions view. No RSU rule is pre-populated; RSU rules are added in the Rules view for the broker's vesting Action text.
    - Reinvestment - a new entry type=Trade is created in the Transactions table and handled as Trade (e.g. dividend reinvestment buys more shares). Reinvestments into cash-like assets such as SPAXX or FDRXX are matched by a separate rule ordered before the generic REINVESTMENT rule (rule 45) with the Effect Other, so they are recorded with type=Other and nothing else is affected; the list of cash-like assets can be edited in that rule.
- Sign (optional, +1 or -1; if set, the sign of the Amount is forced regardless of how the import file signs it)
- Description (text, free-form explanation of the rule)
- Active (flag whether the rule is active, default is yes, inactive rules are considered deprecated)

Imported rows are prepared before the rules are applied:
1. empty rows before the header row are discarded
2. trailing rows after the last transaction row are discarded: a trailing row is one whose column count differs from the header row, or whose Date does not parse (e.g. broker disclaimers at the end of a Fidelity export)
3. the remaining transaction rows are sorted chronologically, earliest date first (rows with the same date keep their order from the file, reversed when the file is sorted newest first) and processed in that order

Rules are applied to every remaining row. A rule with Symbol_Required set is not attempted for rows with an empty Symbol, so rows without a symbol (e.g. interest, margin interest, deposits, withdrawals) are matched only by rules that do not require a symbol. Rows that match no rule are reported as unrecognized.

The Rules table is pre-populated with the following rules when a new database is created:

Transfer transactions are cash flows into or out of the portfolio, not gains or losses, and should be excluded when calculating portfolio performance (e.g. YTD or 1 year change).

## App logic changes

1. Portfolio view should reflect currect portfolio state based on the active Ledger entries and latest prices from the Prices table. It displays one row per symbol (summed across accounts, entries with quantity 0 excluded) with the calculated gain/loss. Drilling down into a symbol shows the equity allocation per account with the averaged cost basis per account. The Portfolio view does not display options.

2. Assets view should display the latest note available. If a new note is entered, if should be added to the Notes table. Action column should be added and should provide Notes action button if Notes are available. When user click on the Notes action button a popup window should display all available notes in a chronological order and have a scroll bar if neeeded.

3. Ledger view should be added by repurposing the current Transactions view (its tab code and layout) and wiring it to the View > Ledger command. It displays active ledger (Active = 1) entries with quantity not equal to 0, with the following columns: Account, Symbol, Quantity, Price, Cost Basis. Price should be calculated as average price from Cost Basis and Quantity. An edit form should be provided at the bottom to allow manual editing and deactivation of ledger entries; a manual edit supersedes the entry (Parent_ID set, Transaction_ID empty). A Rebuild button rebuilds the ledger (and options) of the selected entry's account from its valid transactions after displaying a warning that the rebuild discards any manual edits.

4. Options view should be added to display active options (Active = 1, quantity not 0, and not expired) with the following columns: Account, Symbol, Asset, Expiration Date, Strike, Quantity. An edit form should be provided at the bottom to allow manual editing and deactivation of option entries.

5. The Import (renamed as Import Holdings) logic should change as follows:
- Import Holdings replaces the account's current state with the snapshot in the file (re-importing a fresh positions file is supported):
    - for every equity or option symbol in the file, the account's quantity and cost basis are **set** (not added) to the values from the file; the existing entry, if any, is superseded
    - active Ledger and Options entries of the account whose symbols are not in the file are deactivated
    - the cash balance is **set** to the cash total from the file (see cash holdings below)
- cash holdings: rows whose symbol matches `^SPAXX(\*+)`, `^USD(\*+)`, or `^Cash` (case sensitive; e.g. "SPAXX**", "USD***", "Cash & Cash Investments") represent the account's cash, not an equity holding. They are not inserted as equity Transactions, not added to the Assets table, and do not create Ledger entries. Instead, their values are summed (the Current Value column; if it is not available, the Quantity column, since money market shares are valued at $1, or the Cost Basis column) and the account's cash balance is set to that total. The change is recorded in the Transactions table as a single cash transaction dated with the import's transaction date, with type=Cash, Effect Cash, Description "Opening cash balance" and Amount equal to the total minus the account's current cash balance (so the resulting balance equals the total). If the file has no such rows, the account's cash balance is not changed.
- imported equity and option holdings should be first inserted as Transactions of type Record and Effect Snapshot with the purchase price calculated as the cost basis divided by the number of units or imported from the file (if available). For options the number of units is the number of contracts multiplied by 100, since each option contract represents 100 units. The transaction date taken from the input file (if availble) or entered by the user (ask for one transaction date per file import).
- corresponding Ledger entries should be created or superseded for the imported account + equity symbol pairs (see the Ledger table definition). Cost basis for the ledger entries should be taken from the input file or calculated based on the purchase price and number of units.
- corresponding Options entries should be created or superseded for the affected account + option symbol pairs if there are any options holdings (see the Options table definition)
- the Prices table should not be updated (change from the current logic!)
- the Assets table should be updated with new equity assets per the existing logic, but there is no longer a foreign key dependency on the Asset table, asset entries should be created (if needed) after the transaction and ledger entries. 

6. The added Import Transactions command should have the following logic:
- imported rows are prepared (empty pre-header and trailing rows discarded, remaining rows sorted chronologically, earliest first, see the Rules table definition) and then added to the Transactions table in that order using the import rule matching logic. Records whose Hash matches a transaction recorded in the Transactions table before the import started should be skipped as duplicates. Records are not compared against other records from the same file, so identical rows within one file (e.g. two identical fills on the same day) are all imported, while re-importing the same file skips all of its rows (they are not inserted and have no effect on the Ledger, Options, or cash balance)
- after the file import is completed, a summary should be reported with the number of transactions imported (inserted into the Transactions table), the number of transactions ignored because of the import rules (e.g. JOURNALED), the number of transactions skipped because of an existing matching Hash, and the number of unrecognized transactions (rows whose Action does not match any import rule). Unrecognized rows are not imported; they are listed in the summary (date, action, symbol, quantity, amount) in a scrollable list so that new import rules can be added for them. The summary also lists any imported transactions that predate existing transactions for the same account + symbol pair, since the ledger was then updated out of chronological order and might need to be rebuilt
- equity trades should be reflected in the Ledger table by updating the correspnding ledger entries after each trasnaction. If a ledger entry quantity becomes 0 after the last transaction, ledger entry should still remain active until manually deactivated. a modified ledger entry for the same account + symbol pair supercedes the previous entry which is marked inactive and linked to the new entry via Parent_ID.
- option transactions should be reflected in the Options table. option symbols follow the following format: <Ticker><YYYY><MM><DD><C|P><Strike> e.g. NVDA20260101C300 where C is call, P is put, and 300 is the strike price (fractional strikes keep their decimals, e.g. NVDA20260101C182.5). The number of contracts is not part of the symbol; it is tracked in the Quantity field. a modified option entry for the same account + option symbol pair supercedes the previous entry which is marked inactive and linked to the new entry via Parent_ID. expired option position transactions should be ignored, the experiation date of the option already provides the necessary info. rolled forward options will be equivalent to closing the existing position (buying) and opening a new position (selling).
- transactions of type Trade or Cash will impact the account cash balance: total amount of purchases is subtracted from the cash balance, total ammount of sales is added to the cash balance, dividend payouts are added, interest is added, margin interest subtracted, etc. The cash balance is changed by the transaction's Amount: if the Amount is available in the import file it is used as is, otherwise the Amount is calculated from the price and the number of units (-Quantity × Price, × 100 for options) and stored in the Transactions table.
- the Prices table should not be touched (change from the current logic!), except that missing closing prices for RSU transactions are retrieved and stored (see the RSU effect)
- the Assets table should be updated with new assets per the same logic as for Import holdings. 
- when importing transactions, the transaction category and its effect are inferred from the Action column using the active rules in the Rules table (see the Rules table definition): rules are evaluated in Rule_Order and the first matching rule wins. Rows that match no rule are reported as unrecognized. New rules can be added in the Rules view.

7. Enter transaction function on the Portfolio view should be updated to work in the similar way as the Import Transactions command for both equities and options. An optional transaction date can be entered e.g. "+1000 AAPL $350 2026-09-30". If date is not entered, current date should be used as the transaction date. Note the change of format from using "@<space>" to using "$" sign in front of the price; the "@" format is no longer accepted.

8. Update prices command should retrieve historic stock price data starting from the same date one year ago (today - 1 year) or from the day after the last date the equity price is available in the Prices table, whichever is later. For each new daily closing price an entry should be added to the Prices table. Only the assets corresponding to the active Ledger entries with quantity not equal to 0 should be considered for the price update. If price data covering the last year is not available when a 1 year change is calculated or charted, an error message should be displayed.

9. Rules view should be added to display the active import rules ordered by Rule_Order, with the following columns: Order, Pattern, Case Sensitive, Symbol Required, Category, Effect, Sign, Description. The form at the bottom follows the standard 3-column layout: left column - Pattern, Description, Case Sensitive (checkbox), Symbol Required (checkbox); middle column - Order, Category (dropdown), Effect (dropdown), Sign (dropdown: none, +1, -1); right column - New, Delete, Accept buttons. New clears the form for a new rule; Accept saves the new or edited rule after validating that the Pattern is a valid regular expression (an inline error is shown otherwise); Delete marks the rule inactive. Changes to the rules apply to subsequent imports only; already imported transactions are not re-classified.

10. All views should be closeable.

11. Transactions view (View > Transactions) should be built on the new Transactions table and display valid transactions (Valid = 1) with the following columns: Date, Account, Type, Category, Symbol, Quantity, Price, Amount, Description. It can be pre-filtered by account and/or symbol (the symbol hyperlinks in the Portfolio, Assets and Prices views open it filtered by symbol). An edit form at the bottom allows editing and deleting transactions following the rules in the Transactions table definition (edit, cash delta, delete with warning).

12. All code that reads the Ledger and Prices tables (Accounts balance, Assets quantity, Reports, Analysis, Export, delete reference checks) should be updated to handle the new data schema correctly.

## Deferred to a later version

The following objectives are not implemented in version 2.0; the data needed for them (transactions, ledger history, daily prices) is collected so they can be added later:
- realized taxable gains and losses report
- portfolio balance history / trend chart
